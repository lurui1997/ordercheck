# OrderCheck PRD

版本：2026-10-24。产品暂用名 OrderCheck（跨境订单漏项核对助手）。

本文对齐 `docs/handoff/README.md` 与 `docs/handoff/demo-scenario.json`。品类是开发用的定制礼品包装，不是已经验证过的市场结论。样例交易全部是模拟数据。

## 问题

跨境买卖双方往往已经来回写过几封邮件，卖方准备发订单确认或形式发票时，关键条件却还没有落在同一件事上。日期可能相同，但一个是到货、一个是提货。样品版本可能互相矛盾。买方提到的附件，报价里可能根本没定价。

这些缺口如果到生产或出运之后才被发现，会变成返工和争议。OrderCheck 在发确认之前把缺口指出来，并要求每条判断都能回到原文。

## 用户

- 主要用户：小型出口商的销售或订单负责人。演示里是卖方 Lin。
- 对话另一方：海外采购商。演示里是英国买方 Emma。
- 使用时刻：卖方准备发送订单确认或形式发票之前。
- 不是用户：报关行、物流商、支付机构，也不是要在这个产品里下单的消费者。

系统只处理用户交给它的这一张订单。不读取私人邮箱历史，不跨订单推断。

## 要完成的工作

1. 在发确认之前，看出双方还没对齐的关键事项。
2. 点开一条事项，就能看到原文、缺口和建议问句。
3. 把要问的事项收成一封可编辑的英文邮件，确认之后才发出。
4. 对方回复后，只更新相关事项。含糊说法不能把事项关掉。
5. 双方明确接受之后，得到一份约定摘要。摘要要把已确认、未确认和已接受风险分开，并且不能写成已经履约。

## 范围

### P0 要做

- 一张订单工作台：订单名称、买卖方、邮箱、阶段、邮件和报价文本。
- 一键加载 DEMO-001。
- 核对三个高优先级问题：到货/提货里程碑、样品 v1/v2、内托范围和费用。
- 固定清单上的次要缺口仍然可见：运费、付款、验收。
- 数量 1,000 套显示为双方已确认，不再追问。盒子单价和整套价格分开。
- 问题卡片：证据、缺口、建议问句、状态、等待谁、更新时间。
- 证据引用必须能在指定消息里定位。找不到的句子不能显示成事实。
- 可编辑英文确认邮件。样例模式的“发送”只记录外发，不声称已投递。
- 按样例回复序列更新状态，也允许手工粘贴回复。来源标签写明是样例回放或手工录入。
- 人工标记：接受风险、需要人工核实、本次不适用。必须有理由和操作者。
- 约定摘要。
- 页面上能看出当前是 DEMO_MODE 还是 AWS_MODE。
- 空状态、失败状态、重复消息。

### P0 不做

- 电商、支付、物流跟踪、报关、自动签合同。
- 咸鱼、WhatsApp、未授权邮箱。
- 判断货物实际质量，或承诺交易安全。
- 自动裁决法律、税费和贸易术语。
- 个人知识库、专用模型训练、向量检索。
- 每句话都推送提醒。
- 把样例回放伪装成 SES 收件。
- 公网接口伪造买方确认。

PDF、图片 OCR、真实 SES 收发和 Bedrock 调用不在这一版可运行闭环里。目标形态写在架构文档里，代码里只留接口和明确的未接通错误。

## 用户旅程

1. 卖方打开工作台，看到任务说明，加载 DEMO-001。
2. 左侧出现三封英文邮件和报价。右侧还没有结论。
3. 卖方点击「开始核对」。右侧出现三个重要问题和三个次要缺口，以及已经明确的数量。
4. 卖方点开引用，左侧对应句子被标出。
5. 卖方生成确认邮件，可以改收件人和正文，然后确认记录发送。样例模式写明没有调用 SES。
6. 卖方按顺序回放买方和卖方的后续回复。只确认样品版本的回复，不会关掉日期和内托。
7. 卖方提出整套新条件后，相关事项变成「待对方接受」，不会直接变成已确认。
8. 买方逐项接受后，摘要显示关键约定已确认，同时写明履约还没开始。
9. 可选：回放含糊回复，什么都不关闭；或在确认之后回放改口，只重开样品版本。

闭环的终点是「关键约定被双方明确接受」，不是货已发出，也不是文件具有某种法律效力。

## 黑客松演示的成功标准

这些是可以当场复核的计数，不是节省成本或纠纷下降的估计。

| 指标 | DEMO-001 上的期望 |
|---|---|
| 预设高优先级漏项发现数 | 3 |
| 高优先级里的无关提示 | 0 |
| 证据引用能在指定消息中找到 | 100% |
| 只确认样品版本的回复 | 只关闭 `sample_version` |
| 含糊回复 | 不关闭任何事项 |
| 最终摘要 | 已确认、未确认、已接受风险分开；履约状态未知 |

三分钟演示脚本以交接文档第 11 节为准。公开样例把「真实 SES 收发」替换成标明来源的回放；正式接入 AWS 后再保留真实 message id 和投递事件。

## 非目标

- 不证明这是新品类的市场需求。
- 不把演示订单说成已经节省了多少钱或减少了多少争议。
- 不把规则引擎的输出说成 Bedrock 的输出。
- 不把样例记录发送说成邮件已经送达。
- 不自动替任何一方承诺价格、交期、付款或补救。

## 验收标准

与交接文档第 13 节对齐，并按当前可运行范围划分。

已由样例闭环和自动化测试覆盖：

- 初始材料找出三个重点问题，不把相同日期的不同里程碑当成已经一致。
- 每条展示出来的引用都能在对应消息里找到。
- 不重复询问已明确的数量；盒子价格和整套价格分开。
- 卖方只回复确认 sample v2 时，只推进版本问题。
- 「应该赶得上」「as discussed」「should be fine」不能确认具体到货承诺。
- 卖方提出新条件后，状态停在待买方接受，并保留来源。
- 同一封样例回复重复入账不会再改状态，也不会再记一封发送。
- 最终摘要只收录双方明确同意的内容，并保留未确认项和已接受风险。
- 加载样例、空回复、缺少理由、AWS 未接通时，界面或接口有清楚状态。

尚未在这个仓库里完成，不能算通过：

- 至少一次真实 SES 发信、收件和投递事件。
- Bedrock 对非样例邮件的核对。

这两项的接口、环境变量和失败行为已经留好，见 `docs/ARCHITECTURE.md`。
