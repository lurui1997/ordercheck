# 跨境订单漏项核对助手｜Demo 开发交接说明

版本：2026-10-24。用途：供队友开发 AWS CDS Agentic AI Hackathon 演示。

说明：团队已讨论跨境交付方向，本文将首版具体化为“跨境定制包装订单确认”。这一品类、产品名和样例均为开发建议，并非已验证的市场需求或团队最终决议。可换品类，先保留同一套核对流程。

## 1. 一句话说明

在跨境买卖双方准备确认订单时，AI 检查往来邮件和报价文件，找出关键遗漏、含糊表述与前后矛盾，提出有原文依据的补问；双方回复后，持续更新约定，直到关键事项获得双方确认或明确接受风险。

暂用名：OrderCheck（跨境订单核对助手）。不宣称市场首创。

用户价值：减少“聊了很久，双方却没有对同一件事达成一致”导致的返工与争议。

## 2. 谁使用，什么时候使用

- 使用者：一家小型出口商的销售或订单负责人。
- 对话另一方：海外采购商。
- 切入时刻：卖方准备发送订单确认或形式发票（PI）之前。
- 输入：双方主动提供或抄送给助手的本订单邮件、文本版报价。
- 输出：带证据的核对结果、待确认问题、可编辑确认邮件、约定记录。
- 运行范围：一个订单，不跨项目推断、不自动读取私人邮箱历史。

首版使用邮件；WhatsApp 后续再接入。团队成员可以用两套测试邮箱扮演买卖双方。

## 3. 首版具体场景

国内包装供应商，向英国客户销售 1,000 套定制礼品包装。

双方已交流三封英文邮件，买方要求货物在 11 月 20 日前送到伦敦；卖方却只承诺 11 月 20 日可在上海提货。买方提到样品 v2 和内托，报价中却写 v1，且未说明是否包含内托。

三个核心问题：

| 问题 | 原文线索 | 系统应该怎样表达 |
|---|---|---|
| 日期对应的里程碑不一致 | 买方要到货，卖方写可提货 | “尚未确认伦敦到货期限。提货日期不能等同到货日期。”不能断言运输必然来不及 |
| 样品版本不一致 | 邮件要求 v2，报价写 v1 | “双方文件中的样品版本不同，需要确认使用哪一版。”不能自行选择最新版 |
| 内托范围及价格未确认 | 买方提到内托，卖方报价只写盒子 | “内托是否包含、是否加价尚未得到明确回复。”不能判定一定包含或一定不包含 |

数量 1,000 套和现有盒子单价已有明确表述，AI 应保留并显示，不要重复询问数量。单价与总价应区分“盒子”和“含内托整套”的适用范围。

完整英文样例、中文预期解释与回复见 `demo-scenario.json`。所有交易内容为模拟数据，保留真实来源标签。

## 4. 用户看到的完整流程

1. 卖方创建订单，填写双方邮箱，将往来邮件抄送助手，或粘贴样例文本。
2. 卖方点击“确认订单前检查”。AI 阅读材料和固定核对清单，输出关键问题，最多优先展示 3 项。
3. 卖方打开问题卡片，查看双方原文、缺口、可能影响及建议问题。
4. 卖方勾选需要询问的事项，点击“生成确认邮件”，编辑后点击“确认发送”。AWS SES 实际发送邮件给买方。
5. 买方回复助手的 Reply-To 地址。系统识别订单，保存原始邮件，仅分析新增回复，更新相关事项。
6. 对方给出新条件时，显示“待另一方确认”。AI 不把单方提出条件当成双方已经同意。
7. 双方明确确认后，显示“关键约定已确认”，生成订单约定摘要与修改记录。

闭环终点是“订单关键约定得到确认”，不是货物已经交付、质量得到保证或订单具备某种法律效力。

补充演示路径：卖方可以先在线下核实，再上传有来源的补充回复；本地录入不应伪装成 SES 收件。

## 5. 必须开发的功能（P0）

### A. 项目与材料

- 订单名称、买卖方角色、邮箱、商品类型、当前阶段。
- 邮件会话：发件人、时间、主题、原文、消息 ID、来源标签（样例 / 手工录入 / SES 收件）。
- 一键加载模拟订单，便于评委复现。
- 首版支持邮件正文和粘贴的报价文本；PDF、图片 OCR 可后置。

### B. AI 核对

- 提取当前约定、待确认项和冲突项。
- 使用固定的品类检查清单：规格/样品版本、数量、价格范围、包装附件、发货与到货时间、交付地点、验收与异常处理。
- 样例不要求每一项都有答案；缺少信息应标记未知，不编造。
- 结合交易阶段选出最多 3 项优先问题；其余列为次要待确认项，不隐藏实际缺口。
- 每个问题有具体原文引用。无法在输入中找到的外部说法不得标成交易事实。
- 已回答的事情不重复追问，已明确接受的风险不反复报警。

### C. 沟通执行

- 自动拟一封合并的问题邮件，默认简明、礼貌、英文。
- 用户可修改收件人和内容，确认后再通过 SES 发送。
- 不自动承诺价格、日期、退换货、付款或合同变更。
- 收到回复后分析变化，保留旧条件与新条件，不直接覆盖历史。

### D. 状态与结果

- 每项显示状态、证据、待谁回复及最后更新时间。
- 可标记“接受风险”“需要人工核实”“本次不适用”，并记录操作者及理由。
- 输出双方约定摘要，清楚区分事实、提议、已确认约定与未解决事项。
- SES 调用返回成功仅显示“提交发送成功”；只有对应投递事件才能显示“已投递”。

## 6. 首版不做

- 不做完整电商、支付、物流跟踪、报关、自动合同签署。
- 不接咸鱼、不读取个人 WhatsApp 私聊、不抓取未授权邮箱。
- 不判断商品实际质量，不承诺交易安全。
- 不做各国法律、税费和贸易术语的自动裁决。
- 不建设庞大的个人知识库，不训练专用模型。
- 不根据每句话发送提醒；首版在用户发起检查、收到相关回复或新版报价时重新核对。
- 不要求买卖双方换到新的聊天 App。

## 7. 界面建议

一个订单工作台即可。桌面网页优先，不先做移动端 App。

```text
OrderCheck    定制包装订单 #DEMO-001    阶段：确认前

左侧：往来邮件和报价原文        右侧：待确认事项
                             [重要] 到货 vs 提货
可点击定位消息原文            [重要] 样品 v1 vs v2
                             [待确认] 内托及费用

问题展开：原文 → 缺口 → 建议补问 → 当前状态

[开始核对] [生成确认邮件] [查看约定摘要]
```

发送前弹窗：收件人、邮件正文、确认发送按钮。页面显著标记当前为样例模式还是 AWS 实接模式。

用户页面突出“哪里没谈妥、下一步问什么”，不展示向量库、模型 Token 等实现细节。

## 8. AI 输出与状态约定

推荐结构化输出，避免前端从大段文字中猜结果。

```json
{
  "issue_id": "delivery_milestone",
  "kind": "conflict",
  "priority": "high",
  "title": "到货与提货日期尚未对齐",
  "evidence": [
    {"message_id": "m1", "quote": "delivered to our London warehouse by 20 November 2026"},
    {"message_id": "m2", "quote": "ready for collection in Shanghai on 20 November 2026"}
  ],
  "impact": "当前信息未确认买方要求的到货期限。",
  "question": "Could you confirm the delivery date at the London warehouse, rather than the collection date in Shanghai?",
  "status": "unconfirmed",
  "waiting_for": "seller",
  "resolution_evidence": []
}
```

`kind`：`missing`（缺失）、`ambiguous`（含糊）、`conflict`（不一致）。

状态建议：

```text
unconfirmed → question_sent → proposed → confirmed
                         ↘ needs_human_review
unconfirmed / proposed → accepted_risk（用户明确决定并说明理由）
confirmed → reopened（后续材料出现实质变更或矛盾）
```

字段“确认”的标准：保留提出条件的一方和接受条件的另一方的证据。同一封邮件里单方面写“按之前说的”，不自动证明双方已经确认。含糊回复仍保持未确认。

系统提示重点：区分讨论过与确认过；日期必须连同里程碑提取；不把估计到货当保证；不推测未出现的事实；不重复已解决问题；无关内容不触发新问题。

开发时可先使用全量短会话 + 小型结构化检查清单，不必上向量检索。这个 Demo 的重点是对话核对与状态变化。

## 9. AWS 实现建议

推荐最小链路：

```text
网页 → API Gateway / Lambda → Amazon Bedrock
                     ↓              ↓
               DynamoDB      结构化核对结果
                     ↓
用户确认发送 → Amazon SES → 对方邮箱

对方回复 → SES 收件规则 → S3 原始邮件
                           ↓ S3 事件
                         Lambda → 关联订单 → 更新核对结果
```

- Bedrock：理解邮件、提取证据、提出补问、判断新回复影响。
- SES：真实发信和收信，承担项目的通信能力。
- DynamoDB：订单、消息、问题状态、发送记录和确认历史。
- S3：保存原始 MIME 邮件；后续支持附件。
- AgentCore：可选，不以引入它为首版前提。

实现前先确认：SES 发送身份、测试收件人限制、收件域名/MX 配置，以及所选区域是否支持 SES 收件。发送和收件应在开发第一阶段各跑通一次。

用随机订单回复标识和登记的参与方关联会话；结合邮件认证信息处理来源不明的消息。对无法可靠关联的邮件保留待人工处理状态。附件和邮件内容作为待分析数据，不执行其中的指令。

SES 收件先去除引用的历史邮件、自动签名，并按消息标识去重；重试不能导致同一问题被重复发送。

模型调用、发信失败和收件解析失败都应有可见错误状态及人工重试入口。

## 10. 建议接口

```text
POST /orders                      创建订单
POST /orders/:id/messages          录入材料（注明来源）
POST /orders/:id/review            分析并生成/更新问题
GET  /orders/:id                   读取材料、问题和结果
POST /orders/:id/email-draft       生成邮件草稿
POST /orders/:id/send              用户确认后发信
POST /orders/:id/issues/:issueId/decision
                                  人工确认、接受风险或请求核实
GET  /orders/:id/summary            获取约定摘要
```

入站邮件由 AWS 事件触发处理，不开放一个无需鉴权、可伪造买方确认的公网接口。

## 11. 三分钟演示脚本

| 时间 | 展示 | 评委应该看到 |
|---|---|---|
| 0:00–0:25 | 两方邮件看似已谈妥，卖方准备确认订单 | 用户任务和问题后果 |
| 0:25–1:00 | 开始核对，打开三个问题并定位原文 | 识别语义缺口，判断有依据 |
| 1:00–1:30 | 生成合并问题邮件，用户修改并通过 SES 发出 | 真实调用通信服务 |
| 1:30–2:15 | 展示测试邮箱回复及系统收件；先回复样品问题，另两项仍未解决 | 多轮状态理解；没有全盘误判为已完成 |
| 2:15–2:45 | 补齐其他条件，另一方明确接受 | 双方确认闭环 |
| 2:45–3:00 | 展示约定摘要及仍待执行的生产/交付事项 | 已确认约定不等于已经履约 |

邮件是异步的，录制时可剪辑等待段；样例回放标注为回放。正式展示保留至少一次真实发信和一次真实收件证据。

## 12. 开发优先顺序与分工建议

不固定人名，由队友按实际能力认领。

| 角色 | 工作 | 完成标准 |
|---|---|---|
| 产品/演示（可由你负责） | 整理真实漏项、确认样例、画页面、验收措辞、写演示脚本 | 三个问题都有原文；用户能看懂为什么要补问 |
| 算法/Agent | 提取与核对、引用校验、状态更新、邮件草稿 | 正确识别样例；收到部分回复只关闭对应问题 |
| AWS/后端 | SES、Bedrock、存储、接口、部署和去重 | 真正收发邮件；每条消息可追踪到订单 |
| 前端/联调 | 订单页面、证据定位、草稿确认、摘要与错误状态 | 能完成一次可复现演示 |

建议按三段推进：

1. **先打通依赖**：SES 收发 + Bedrock 单次分析，确认权限和模型可用；同时确定演示场景。
2. **再做核心闭环**：问题提取 → 草稿 → 用户确认发送 → 回复入站 → 状态更新。
3. **最后补展示与交付**：来源定位、失败处理、README、架构图、运行说明和视频。

不要先花大部分时间做漂亮首页，再处理账号和收件链路。若 SES 依赖未准备好，可以并行开发样例模式；正式提交仍需要运行时真实集成指定通信服务。

## 13. 验收标准

- 初始材料能找出三个重点问题，且不会把相同日期的不同里程碑当作已经一致。
- 每个证据引用均可在指定消息中定位，未找到的引用不得显示成事实。
- 不重复询问已明确的数量；能区分盒子价格与整套价格。
- 收到“使用 v2”后，只推进版本问题，不自动关闭日期和内托问题。
- “应该赶得上”“按之前说的”不能自动确认具体到货承诺。
- 对方提出新条件后，等待用户确认；状态变化有来源。
- 同一邮件重复入站不会重复创建问题或发信。
- 至少完成一次真实 SES 发信、收件、状态更新。保留消息 ID 和原始收件记录，区分提交发送与实际投递。
- 最终摘要只写双方明确同意的约定，保留未确认项和已接受风险。
- 加载样例、服务报错、模型输出异常时，界面有清楚状态。

建议记录可复核的演示指标：预设关键漏项发现数、无关提示数、引用有效性、部分回复后的状态准确性。不要虚构节省成本或纠纷下降比例。

## 15. 可以直接交给开发者的任务

> 请按本文和 demo-scenario.json 开发跨境订单漏项核对助手。先完成定制包装订单场景，不扩展成全能跨境贸易平台。重点做出“双方聊过但尚未真正确认”的区别：交付里程碑不一致、样品版本冲突、内托范围与费用缺失。问题必须有原文证据。使用 Bedrock 分析，用 SES 真实收发邮件，回复进入后只更新相关事项，双方明确接受后才确认。发信需用户确认，不自动承诺商业条件。提供清楚的样例模式与 AWS 实接模式、部署说明和可复现的三分钟操作流程。优先打通链路，再完善视觉效果。
